# 让 Agent 填完整个项目

适用于 v0.2.1 的完整项目配置。目标是让 Agent 根据你的项目描述填写所有相关表单，再通过文件导入到看板。软件不运行内置模型，也不会把数据自动发给外部 Agent。

## 第一次使用

1. 准备项目想法、使用者、首版范围和合作情况。不知道的内容可写“待确认”。
2. 将 [完整模板](project-template.json)、[JSON Schema](project.schema.json) 和下方提示交给 Agent。也可以从软件保存当前项目的配置文件，这会包含已经填写的内容。
3. 让 Agent 返回 UTF-8 JSON 文件。不要把 JSON 放在 Markdown 代码围栏里保存，不要加入注释或未定义字段。
4. 在项目页点击“Agent 填写项目”，或在现有项目点击“导入 / 导出项目信息”，选择 JSON 文件或粘贴内容，点击“校验并预览”。
5. 确认创建或更新后，项目基本信息和开发流程表单会一起填好。

软件里的“复制给 Agent”会自动包含填写规则、当前项目内容和完整 JSON Schema；使用该按钮时，不必另行手动拼接字段说明。配置不包含 `logUpdate`，因为“同时记入工作流水”是一次性操作而非项目信息，导入最新进展不会重复生成流水。

`project-template.json` 与软件中的完整项目模板使用同一份定义。它包含填写位置和默认的新手路线，不是已经完成的项目计划。名称和目标中的“待填写”需要替换；不需要的示例参与人、任务或沟通记录可以在新建文件中删去。`evidence`、接收确认和验收结果应保留为空，直到真的执行并验证。

## 可复制给 Agent 的说明

> 请根据我的项目描述，填写附带的 `kanban-project` JSON 模板。结构必须符合 `project.schema.json`，不要添加未知字段。项目描述：〈在这里写项目想法〉。
>
> 填写项目名称、说明、负责人、当前状态和真实进度；补充项目目标、首版范围、暂不做事项、能实际检查的验收标准。选择适合的开发路线和协作方式，将首版拆成少量可交付的里程碑，为近期里程碑添加可执行的小任务，并填写责任边界、输入、输出、依赖和验收标准。多人合作时补充参与人、待确认问题和交接要求。
>
> 不知道的人员、日期、联系方式或技术结论不要编造：可空的字段留空；需要后续确认的问题放入 `decisions`，状态为 `pending`。只做规划时，任务为 `todo`，`hasStarted` 为 `false`，交接为 `draft`，验证证据为空。没有实际验证时不得声称完成、接收或验收通过。
>
> 新建项目时省略 `project.id`，让应用生成。修改已有项目时，以我从软件导出的文件为基础，保留项目和所有既有条目的 id，不要把修改目标当作新项目。新增条目使用新的稳定 id，依赖只能引用本文件中已有任务 id，禁止循环依赖。
>
> 返回一份完整、可以保存为 UTF-8 的 JSON 文件；不要只返回补丁或片段。先列出必须由我回答的问题，得到答案后再定稿；如我要求先给草稿，保留待确认项即可。

## 文件层级

```text
schema_version: 1
kind: kanban-project
project
  基本信息
  workflow（普通项目可以不设置）
    目标与开发路线
    participants：参与人
    milestones：里程碑
    tasks：开发任务与交接
    decisions：沟通、变更与接口约定
```

## 项目基本信息字段

| 字段 | 填什么 |
| --- | --- |
| `project.id` | 新建时省略；修改已有项目时保留导出的值 |
| `name` | 项目名称，必填 |
| `description` | 背景、使用场景和项目说明 |
| `owner` | 项目负责人姓名；是本地文字记录，不是账号 |
| `state` | `unstarted` 未开始、`active` 进行中、`paused` 暂停、`completed` 已完成 |
| `progress` | 0–100 的人工进度值；不会代替里程碑和任务验收 |
| `update` | 真实的最新进展。导入此字段不会另行生成一条进展流水 |
| `archived` | 是否归档；通常为 `false` |
| `workflow` | 以下开发流程对象；新建普通项目可以省略 |

基本信息使用完整配置语义：省略可选字段会恢复该字段默认值，预览会显示变化。更新已有项目时若省略 `workflow`，原开发流程保留，不会被清空。

## 开发路线与目标字段

| 字段 | 填什么 |
| --- | --- |
| `mode` | `novice` 新手带做、`prototype` 原型验证、`agile` 敏捷迭代、`kanban` 持续看板、`staged` 阶段交付、`shapeup` 限定投入 |
| `collaboration` | `solo` 个人、`team` 小组、`cross` 跨部门／委托 |
| `guidance` | `detailed` 详细引导、`compact` 精简引导 |
| `wipLimit` | 同时进行任务的提示上限，1–20，个人可填 1 |
| `goal` | 为谁解决什么问题，希望得到什么结果 |
| `scope` | 本次必须交付的范围 |
| `outOfScope` | 明确暂不做的内容 |
| `acceptance` | 项目验收清单；字符串中可用换行分隔 |

## 参与人和里程碑字段

`participants` 每项包含：`id` 稳定标识、`name` 姓名、`role` 角色及责任、`contact` 联系方式或联系备注。姓名与任务中的人员字段是文字，不是在线账号关联。

`milestones` 每项包含：

| 字段 | 填什么 |
| --- | --- |
| `id`、`title` | 稳定标识和一个可观察的阶段结果 |
| `goal` | 这一阶段要得到什么 |
| `acceptance` | 怎样判断阶段目标达到 |
| `state` | `pending` 待推进、`active` 当前推进、`completed` 已验收 |
| `dueDate` | `YYYY-MM-DD` 目标日期，未知时 `""` |
| `evidence` | 实际验收依据，尚未验证时 `""` |

## 开发任务字段

| 字段 | 填什么 |
| --- | --- |
| `id`、`title` | 稳定标识和可以执行、验证的小任务 |
| `milestoneId` | 所属里程碑 id，未关联填 `""` |
| `owner` | 一名主要负责人 |
| `contributors` | 协助人，可用文字列出多人 |
| `reviewer`、`receiver` | 谁验收、交给谁接手；不需要时留空 |
| `boundary` | 我负责到哪里，本任务不包含什么 |
| `input`、`output` | 需要谁提供什么，以及交出什么给谁继续 |
| `acceptance` | 样例、操作和预期结果 |
| `dependsOn` | 前置任务 id 数组，无依赖时 `[]` |
| `state` | `todo` 待开始、`doing` 进行中、`review` 待验收、`done` 已完成 |
| `hasStarted` | 是否已经操作；新任务填 `false`，导出后保留，不可用它清除历史保护 |
| `priority` | `high` 优先、`normal` 普通、`low` 稍后 |
| `blocker` | 卡点、解除条件及需要联系的人 |
| `followUpDate` | `YYYY-MM-DD` 跟进日期，未知时 `""` |
| `evidence` | 实际处理和验证结果，尚未执行时 `""` |
| `handoff` | 下方交接对象；没有交接也可以保留模板中的空值 |

`handoff` 的字段：

| 字段 | 填什么 |
| --- | --- |
| `status` | `draft` 准备交接、`submitted` 已提交、`received` 已接收、`accepted` 验收通过、`returned` 退回补充 |
| `artifacts` | 交付物、版本和位置；不自动上传文件 |
| `instructions` | 启动、使用或接手方法 |
| `verification` | 已验证场景和真实结果 |
| `risks` | 已知问题、限制及影响 |
| `nextAction` | 接手后的下一步和责任人 |
| `note` | 谁何时确认接收、退回需要补什么等实际沟通记录 |

## 沟通记录字段

`decisions` 每项包含：

| 字段 | 填什么 |
| --- | --- |
| `id`、`topic` | 稳定标识及需要讨论或确认的问题 |
| `kind` | `decision` 需求／决定、`change` 范围变更、`interface` 接口约定 |
| `people` | 相关人员与需要谁确认 |
| `conclusion` | 真实结论；未确认时可记录待讨论方案，不编造同意 |
| `impact` | 对范围、时间、已有工作和下一步的影响 |
| `date`、`followUpDate` | 沟通日期、跟进日期；使用 `YYYY-MM-DD` 或 `""` |
| `status` | `pending` 待确认、`confirmed` 已登记确认 |

接口约定可以在 `conclusion` 中按“输入、输出、格式样例、失败处理、联调时间、变更通知人”写清楚。格式仍为普通字符串，不要自行增加 Schema 外的键。

## 新建、更新与导入边界

- 项目页的全局入口允许新建项目。没有 `project.id` 时，每次确认都会创建新项目；重复预览不写入。首次创建后，请导出带真实 id 的配置继续修改。
- 从某个项目打开完整配置入口时，目标绑定该项目。文件里省略项目 id 会使用当前项目；明确填了另一个 id 会被拒绝。
- 相同项目 id 更新基本信息；流程内的参与人、里程碑、任务、沟通按稳定 id 合并，文件未出现的已有条目不会删除。
- 已操作任务、已完成里程碑和已确认沟通受到保护；请勿为绕过保护而改变 id，需要新任务时才新增 id。
- Agent 声称完成的新任务会进入待验收，接收／验收状态不会替他人确认。既有人工完成依据保留。
- 预览绑定数据版本。数据变化后应重新预览再确认；校验错误整次不写入。
- JSON Schema 负责结构；应用还会检查真实日期、重复 id、里程碑引用、任务依赖及完成条件。单文件最多 500 项开发任务、100 个里程碑、100 个参与人和 500 条沟通记录。
- 完整项目配置不包含普通笔记、工作流水、日期事项或周期检查。它用于填项目表单，完整数据迁移仍使用备份。日期事项仍使用 `kanban.schema.json`，旧开发流程格式仍使用 `workflow.schema.json`。
- 导出包含流程中显式填写的人员联系方式、决定和交付物位置。交给外部 Agent 前先查看预览，应用不会自动发送。

从共享契约重新生成模板与 Schema：`npm run schema:project`。
